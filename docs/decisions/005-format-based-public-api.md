# 005 - Format- and operation-based names in the public API

> Historical planning/research/decision record. The dated findings are preserved; use [the v1.0.0 documentation index](https://github.com/chto0703009/InkProf-public/blob/main/docs/README.md) for current usage and status.

Date: 2026-09-25. Status: decided by the project owner and implemented.

## Decision

InkProf's public MATLAB API is named after **the operation and the data format**, not after a program or vendor that produces or uses the format.

This applies within an independent open-source project under `GPL-3.0-or-later`. Factual interoperability documentation matters, so that users can understand open workflows without InkProf being presented as a product from, or approved by, a third-party vendor.

An import, rendering or export must therefore be describable without the API name implying that the third-party program is required, controls the process or owns the internal workflow. For example, PXF and RGB CGATS are encoded to TIFF16 with:

```matlab
inkprof.createTiff16(...)
```

TXF export is done with:

```matlab
inkprof.exportTxfTarget(...)
```

A compact single-page A4 layout is chosen with:

```matlab
CompactA4=true
```

## Renames carried out

| Previous name | Decided name |
|---|---|
| `inkprof.createI1ProfilerTiff` | `inkprof.createTiff16` |
| `inkprof.exportI1ProfilerTarget` | `inkprof.exportTxfTarget` |
| `I1ProfilerA4=true` | `CompactA4=true` |

The previous names are removed rather than kept as parallel aliases. The project is still at an early stage of development, and a single unambiguous API outweighs backward compatibility with the short-lived names.

## Naming rule

- The function's verb describes the action, for example `create`, `import`, `export` or `verify`.
- The rest of the name describes the result or format, for example `Tiff16`, `TxfTarget` or `Cgats`.
- Vendor and product names are not used in public function or option names when the format or operation is enough to describe the behaviour.
- Product names may be used in documentation, test fixtures, provenance and compatibility reports when the actual source or recipient needs to be stated.
- A vendor-specific name requires a new explicit design decision, and only if the behaviour really is bound to a proprietary API and cannot be described correctly by format or operation.

## Trademark rule

- InkProf does not use third-party trademarks in the project name, logo, public API names, generated image headings or the TIFF `Software` field.
- A third-party name may only be used descriptively, when it is needed to identify a file's origin, a tested program version, compatibility or an intended recipient.
- Descriptive use must be factual and must not imply partnership, certification, sponsorship or approval.
- Third-party logos, visual identity and copyright text are not copied into files generated by InkProf.
- Generated files identify InkProf as the sender. Reference files are kept separately and unchanged, for verification and provenance.
- The README and distributed documentation state that third-party names belong to their respective rights holders and that InkProf is an independent project.

## Rationale

PXF, TXF and CGATS appear in workflows with several tools. A product name in the function name makes the API narrower than the data flow and can wrongly suggest a program dependency. Format-based names make it clearer what the function reads, creates or exports, and give a more stable API if more compatible producers or recipients are added.

The decision does not change compatibility status. A TIFF layout or TXF export may still be based on an observed reference and still lack full physical verification. Such limitations are to be stated in the result metadata and documentation, neither hidden nor overstated by the function name.
